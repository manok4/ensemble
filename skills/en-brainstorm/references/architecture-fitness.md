# Architecture fitness — the contract

Ensemble defines *what* the architecture-fitness check looks like; **the project provides the implementation**. This split keeps Ensemble language-agnostic while letting projects encode their actual layer rules in whatever AST tool, parser, or linter library is best for their stack.

## When this fires

`bin/ensemble-lint` invokes the project's fitness checker when **both** are true:

1. `.ensemble/config.local.yaml` declares:
   ```yaml
   fitness:
     enabled: true
   ```
2. The project ships an executable at the configured path (default `bin/check-fitness`).

If `fitness.enabled: true` but the executable is missing, ensemble-lint emits a P3 `architecture.fitness-checker-missing` finding so the gap is visible.

## The contract

### Inputs

The fitness checker reads on **stdin** a newline-separated list of changed file paths:

```
src/services/notifications.ts
src/utils/format.ts
tests/services/notifications.test.ts
```

The list is generated by `git diff --name-only HEAD` (uncommitted + staged). If the working tree is clean, ensemble-lint feeds it `git ls-files` instead.

The checker can ignore unfamiliar paths (e.g., `tests/**`, `docs/**`) — its job is to enforce architectural rules on source code.

### Outputs

The checker writes **JSON-lines** to stdout — one finding per line:

```json
{"rule": "architecture.layer-violation", "file": "src/types/user.ts", "line": 12, "severity": "P1", "message": "Layer 'Types' imports from 'Service'; layer rule: Types may only depend on standard library", "remediation": "Move the imported helper to Repo or Service layer, or invert the dependency"}
{"rule": "architecture.public-api-export", "file": "src/repo/users.ts", "line": 5, "severity": "P2", "message": "Public-API export missing JSDoc", "remediation": "Add a /** ... */ block describing parameters and return type"}
```

### Required JSON fields

| Field | Required | Type | Notes |
|---|---|---|---|
| `rule` | yes | string | Dotted ID, e.g. `architecture.layer-violation`. Defaults to `architecture.fitness-violation` if omitted. |
| `file` | yes | string | Repo-relative path |
| `line` | optional | int or null | Line number; null/omit for file-level findings |
| `severity` | yes | `"P0"` \| `"P1"` \| `"P2"` \| `"P3"` | P0 = security/correctness blocker; P1 = correctness/maintainability blocker; P2 = advisory; P3 = informational |
| `message` | yes | string | Human-readable description |
| `remediation` | yes | string | One-line suggested fix |

### Exit codes

| Code | Meaning |
|---|---|
| `0` | No violations |
| `1` | One or more violations (printed as JSON-lines on stdout) |
| `2` | Checker error (e.g., misconfiguration, parse failure) |

ensemble-lint reads stdout regardless of exit code — it expects findings on stdout even when the checker exits 1.

## Example: a layer-rules checker (TypeScript project)

A project enforcing `Types → Config → Repo → Service → Runtime → UI` could ship a `bin/check-fitness`:

```typescript
#!/usr/bin/env tsx
// Project's own implementation. Ensemble doesn't ship this — you do.

import { readFileSync } from "fs";
import { parse } from "@typescript-eslint/parser";

const LAYER_RULES: Record<string, string[]> = {
  types:   [],                                  // Types depend on nothing
  config:  ["types"],
  repo:    ["types", "config"],
  service: ["types", "config", "repo"],
  runtime: ["types", "config", "repo", "service"],
  ui:      ["types", "config", "repo", "service", "runtime"],
};

function layerOf(path: string): string | null {
  const m = path.match(/^src\/(types|config|repo|service|runtime|ui)\//);
  return m ? m[1] : null;
}

const changed = readFileSync(0, "utf8").split("\n").filter(Boolean);
const findings: any[] = [];

for (const file of changed) {
  if (!file.endsWith(".ts") && !file.endsWith(".tsx")) continue;
  const myLayer = layerOf(file);
  if (!myLayer) continue;

  const allowed = new Set(LAYER_RULES[myLayer]);
  const src = readFileSync(file, "utf8");
  const ast = parse(src, { loc: true });

  for (const node of ast.body) {
    if (node.type !== "ImportDeclaration") continue;
    const importedFrom = node.source.value;
    if (typeof importedFrom !== "string" || !importedFrom.startsWith("../")) continue;
    const targetLayer = layerOf(importedFrom.replace(/^\.\.\//, "src/"));
    if (!targetLayer) continue;
    if (!allowed.has(targetLayer)) {
      findings.push({
        rule: "architecture.layer-violation",
        file,
        line: node.loc.start.line,
        severity: "P1",
        message: `Layer '${myLayer}' imports from '${targetLayer}'; allowed: ${[...allowed].join(", ") || "(none)"}`,
        remediation: `Move the symbol up to a lower layer, or refactor to invert the dependency.`,
      });
    }
  }
}

for (const f of findings) console.log(JSON.stringify(f));
process.exit(findings.length > 0 ? 1 : 0);
```

The same pattern works for any language — Python (`ast` module), Go (`go/parser`), Rust (`syn`), etc. The contract is uniform.

## Where the rules live

Two acceptable locations:

1. **In `.ensemble/fitness.yaml`** — declarative. The project's `bin/check-fitness` reads this file to know what to enforce. Recommended for cross-team consistency.
   ```yaml
   layers:
     - name: types
       depends_on: []
     - name: service
       depends_on: [types, config, repo]
     # ...
   public_api:
     - rule: must-have-jsdoc
       paths: ["src/repo/**", "src/service/**"]
   ```
2. **Hardcoded in `bin/check-fitness`** — imperative. Simpler for small projects; harder to evolve.

Use whichever fits your team's review style.

## How `/en-foundation` interacts

When a new project is set up, `/en-foundation` §9 (Architecture) asks about layer boundaries. If declared, the answer is captured in `docs/foundation.md` and the user is prompted to seed `.ensemble/fitness.yaml` from those answers. The user still has to provide `bin/check-fitness` themselves — Ensemble doesn't auto-generate the checker code.

Future `/en-foundation --generate-fitness-checker <language>` could scaffold a starter implementation; for v1 it's manual.

## How `/en-sweep` and `/en-review` interact

Both call `bin/ensemble-lint`, which invokes the fitness checker. So:

- **`/en-review`** (pre-PR) catches violations before they land.
- **`/en-sweep`** (post-PR-merge) catches violations that slipped through.
- **`/en-resolve-pr`** sees fitness violations as inline review comments (when the Anthropic Code Review action surfaces them).

## Severity policy

| Severity | When to use | Default ensemble-lint behavior |
|---|---|---|
| `P0` | Cross-cutting violation that breaks a security or correctness invariant (e.g., UI layer reaches into Repo, bypassing Service auth) | Blocks `/en-ship` pre-flight; surfaces immediately in `/en-review` |
| `P1` | Layer violation, missing public-API contract, dependency-direction inversion | Surfaces in `/en-review`, `/en-resolve-pr` |
| `P2` | Style/convention finding (missing JSDoc, naming convention) | Surfaces as advisory; `/en-sweep` may auto-fix |
| `P3` | Informational (architecture-doc drift not yet a violation) | Surfaces only in verbose mode |

The checker chooses severity per finding. Ensemble doesn't override it.

## Anti-patterns

- **Don't put business logic in `bin/check-fitness`.** Its job is enforcement of structural rules, not feature validation. Feature tests belong in the project's test suite.
- **Don't have the checker write files.** It's read-only. Mutations are out of scope.
- **Don't make the checker depend on running services.** It runs in CI; it must be self-contained.
- **Don't conflate fitness with style.** Style (formatting, lint-style nits) belongs in language linters (eslint, ruff, clippy). Fitness is about *architecture*.

## Where this fits in the harness

Per Martin Fowler's framing, this is the **Architecture Fitness Harness** — the second of three regulation dimensions. It's one of the harder ones to mature; the contract here is meant to be the smallest viable interface so projects can start cheaply.
